# CLAUDE.md — UseHourly (formerly Hourly)

Time tracking for freelancers. The product name is **UseHourly** (renamed from "Hourly" 2026-10-14 to stay clear of other products called Hourly). Only what people see changed: internal ids are kept on purpose (Worker `hourly`, D1 `hourly-db`, the `hourly:lastProject` saved setting, `hourly_rate` fields). The GitHub repo is `Zontak-LLC/usehourly` and the local folder is `~/Projects/usehourly` (both renamed from `hourly` on 2026-10-14; the old repo URL redirects); download file names are `usehourly-*.xlsx`. Goal: logging a day's time should take seconds (UX is the product).
Built on the `arhamkhnz/next-shadcn-admin-dashboard` shell (the Vercel "admin-dashboard" template was Postgres/Auth.js-only, so it was not used). No Material UI — shadcn + Tailwind only.

## Stack
Next.js 16, React 19, Tailwind v4, shadcn/ui · NextAuth v5 (Credentials, JWT) · tRPC v11 · Prisma 7 + Cloudflare D1 · Vitest · Biome · OpenNext on Cloudflare Workers. Dev port **3028**.

## Commands
```bash
npm run ci                  # EXACTLY what CI runs (biome check on the whole project, tsc, vitest): run it before every push
npm run dev                 # http://localhost:3028 (local D1 via wrangler state)
npm run d1:migrate:local    # apply migrations/ to local D1 (do this first)
npx vitest run              # scenario tests (src/__tests__)
npx next build              # must pass before deploy
npm run deploy              # opennextjs-cloudflare build + deploy
npm run d1:migrate:remote
```
Live at **https://usehourly.app** (Worker `hourly`, Cloudflare account Zontak LLC, custom domain attached in `wrangler.jsonc` `routes`); the `*.workers.dev` address is switched off (`workers_dev: false`) as of the 2026-10-17 security review, so the custom domain is the only public origin (the old `hourly.dzontak.workers.dev` stops answering after the next deploy). `wrangler.jsonc` pins `account_id` because the shared token sees more than one account. `NEXT_PUBLIC_APP_URL` is baked at build time, so `npm run deploy` sets it on the build command.
Secrets: `AUTH_SECRET`, `AUTH_URL` in `.env.local` and `.dev.vars` (keep in sync); production secret via `wrangler secret put AUTH_SECRET`.

## Design decisions
- Duration is integer **minutes**; `TimeEntry.date` is a local `YYYY-MM-DD` string (Workers run in UTC — "today" is computed in the browser, never on the server).
- `src/lib/duration.ts` parses `1.5`, `1:30`, `90m`, `2h`, `1h30`; bare number ≤12 = hours, else minutes. Shared by client preview and server validation.
- Running timer = a `TimeEntry` with `started_at` set. `entry.start` stops any running timer first; stop rounds elapsed up to ≥1 min.
- Multi-tenancy = per-user: every procedure uses `protectedProcedure` and filters by `ctx.userId` (that filter is the isolation boundary).
- tRPC router for clients is named `clients` (a router named `client` collides with tRPC's built-in).
- `getPrisma()` is lazy on purpose — a top-level await on D1 breaks `next build` with SQLITE_BUSY.
- `trpc.ts` must not import next-auth/Prisma at runtime (context lives in `context.ts`) so routers are testable.
- Sidebar user name is read from the DB in the dashboard layout, not the JWT (JWT goes stale after profile edits).

## Launch gaps (2026-10-17, issue #33, migration 0017)
- **Delete my account:** `account.deleteAccount({ confirm })` (Account > Your data, `delete-account-card.tsx`). Password accounts confirm with the password, GitHub/Google-only accounts by typing their email; wrong tries share the 5-per-15-minutes limit; demo accounts are refused. `server/account-deletion.ts` deletes children first and the account LAST so a failure can be retried; add any new user-owned table there (a test lists them). Backups with the hosting provider age out within 30 days (stated on `/privacy`).
- **Sign-up bot protection:** a hidden `website` box (filled = refused) plus Cloudflare Turnstile, dormant until `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are set (secret = Worker secret; the site key reaches the form through `account.signupCheck`). A Cloudflare outage counts as a no. The CSP allows `challenges.cloudflare.com` for script and frame. Social sign-up and the demo button are covered by their own IP limits only.
- **Health check:** `GET/HEAD /api/health` answers `{ok}` 200/503 after `SELECT 1`; point an uptime monitor at it (and at `/api/mcp`).
- **Backups:** D1 Time Travel is active on `hourly-db` (30 days on the paid plan): `wrangler d1 time-travel info hourly-db`, restore with `wrangler d1 time-travel restore hourly-db --timestamp=<ISO time>` (overwrites live data; try it only in an emergency). `npm run d1:backup` writes a full SQL dump to `backups/` (git-ignored: it holds everyone's data).
- **Email bounces:** `POST /api/webhooks/resend` (Svix-signed, `RESEND_WEBHOOK_SECRET`, 404 until set). A permanent bounce or spam complaint sets `auth_users.email_bounced_at` and turns the Friday reminder off; transient bounces are ignored. Resend dashboard > Webhooks > `email.bounced`, `email.complained`. Test: `launch-gaps-journey.test.ts`.
- **CI deploy token (issue #33):** `CLOUDFLARE_API_TOKEN` lives in the CircleCI context `usehourly-production` (restricted to `pipeline.git.branch == "main"`), used by the `deploy` job only; pushing to `main` is the release: CircleCI runs the checks, applies D1 migrations, then deploys. Do not also run `npm run deploy` by hand (the owner chose this workflow on 2026-10-17: work locally, a push ships).
- Deploy order: `npm run d1:migrate:remote` (0017) BEFORE `npm run deploy`.

## Usage tracking and Insights (2026-10-17, issue #37, migration 0018)
- **Page views, first-party and anonymous:** `UsageBeacon` (`components/usage-beacon.tsx`, mounted in the dashboard layout) sends the page name on each in-app navigation to `POST /api/usage`, which upserts `usage_daily(day, page, count)`. The page must be one of `USAGE_PAGES` (`lib/usage.ts`, a closed list), so nothing a caller sends can add a row; no user id, cookie, address or content is stored. Signed-out requests and sample accounts get a quiet 204; 120 views a minute per account, extras dropped. `/privacy` says so. Adding a page to count means adding it to `USAGE_PAGES` AND `USAGE_PAGE_LABELS`.
- **Insights page (owner only):** `/dashboard/insights`, `insights.overview`. Access = the `ADMIN_EMAILS` secret (comma separated; a Worker SECRET, not a `vars` entry, because the repo is public) AND a confirmed email (`lib/admin.ts`: anyone can register an address they do not own). Everyone else gets the normal not-found page / `NOT_FOUND`. Shows sign-ups per week, the funnel (signed up, logged time, first entry within a day, made an invoice), active 7/30 days, retention of accounts older than 4 weeks, entries per active account, and page views. The numbers come from `lib/insights.ts` (`buildInsights`, pure) over aggregate queries on existing tables; sample accounts are excluded. Test: `usage-insights-journey.test.ts`.
- Deploy: `npm run d1:migrate:remote` (0018) BEFORE `npm run deploy`, then `npx wrangler secret put ADMIN_EMAILS` (the secret is the owner's address).
- Gotcha hit while building: `echo "X=1" >> .env.local` glues onto the last line when the file has no trailing newline (it corrupted a secret's value). Check `tail -c1` first or use a Python append.

## Client sign-off timesheets (2026-10-17, issue #34, migration 0019)
- **Share for sign-off** (`components/share-timesheet.tsx`, next to Export / Date range on Week and Month): pick a range, one client or project, whether to include the freelancer's descriptions, and a lifetime (7, 30 or 90 days). `timesheetShare.create` recomputes everything from the account's own entries and stores a **frozen snapshot** (`lib/timesheet-share.ts` `buildShareSnapshot`: hours only, no rates or amounts, running timers and zero-minute rows left out), so the client approves exactly what they saw. The link `/timesheet/<token>` is returned ONCE; only its SHA-256 is stored (`timesheet_shares`, `findShareByToken`). Max 50 live links per account; sample accounts cannot share.
- **The client's page** (`src/app/timesheet/[token]/`): public (`route-access.ts` allows `/timesheet/*`; robots.txt disallows it; `noindex`, `referrer: no-referrer`), read-only grid (or a by-day list over 14 worked days), descriptions, a print / save-as-PDF button, and an approval box (name + optional note). Unknown, revoked and expired links all show the same "isn't available any more" page. Approval is one conditional `updateMany` (not yet approved, not revoked, not expired), throttled per connection (20/h) and per link (5/h); `timesheetShare.approve` is the only public procedure. An approved sheet still works until it expires.
- Freelancer side: `timesheetShare.list` (no snapshots) and `revoke` ("Turn off"). Expired links are deleted 90 days after they stop working (`housekeeping.ts`); account deletion removes them too (`account-deletion.ts`; a test lists the tables).
- **Approval email:** when a client approves, `tellOwner` (in `routers/timesheet-share.ts`) emails the owner once (`timesheetApprovedMessage` in `lib/mailer.ts`: subject "<name> approved your timesheet", the sheet's title, the client's note, a link to /dashboard/week; never the private link). Best effort (a failed or missing mailer never blocks the approval) and only to an address that is confirmed, not bounced and not a sample account, so a sheet cannot be used to send mail to an address someone merely registered. The client's typed name is cleaned of line breaks and control characters before it reaches the subject.
- Not built (ideas): an "approved by" line on invoices, a setting to turn the approval email off, a PDF made in the browser (printing the page does the job).
- Test: `timesheet-share-journey.test.ts` (mutation-checked: the account filter on entries and the atomic approval claim; the race test forces both requests to read before either writes).

## Emails: styled HTML plus plain text (2026-10-17, issue #35 step 1)
- Every email is sent as HTML AND text. `lib/email-template.ts` `renderEmail({ title, greeting, blocks, footnote })` renders both from one list of blocks (paragraph, heading, quote, rows, button), so they cannot drift apart; `MailMessage` has an optional `html` and `createMailer` posts `text` + `html` together (a message with no `html` still sends text only). Confirm email, password reset, the Friday reminder and "timesheet approved" all use it.
- Rules the template keeps: everything interpolated is HTML-escaped; links must be http(s) (`safeUrl`: `javascript:`, `data:` and `mailto:` become plain text, never an `href`); no images, scripts, fonts or stylesheets (mail apps block them and they are how mail is tracked); fixed hex colours from the Sunshine palette (mail apps ignore CSS variables) with a `prefers-color-scheme: dark` block; one 560px column; every button is also written out as a pasteable link under it. Text that comes from a stranger (a client's name) is also cleaned for subject lines (`oneLine` in `mailer.ts`).
- Adding an email: build it with `renderEmail`, keep the link a `{ button }` block (the text part then carries the bare URL, which tests rely on to find tokens), and add its case to `email-template.test.ts`. Test: `email-template.test.ts` (mutation-checked: escaping, link schemes). Next on #35: client email addresses, the invoice link page, sending and overdue reminders (plan in the issue).

## Emailing invoices and overdue reminders (2026-10-17, issue #35 step 4, migration 0021)
- **"Email it"** (`components/send-invoice.tsx`, the envelope on each Invoices row; `invoiceMail.send / recipient / setReminders`): sends the client (the address under Billing details) a message from "<seller> via UseHourly" (`MailMessage.fromName`, built by `senderFrom` from the app's own address, name cleaned) with Reply-To = the freelancer's confirmed address, a button to a FRESH private invoice link, an optional note quoted under "A note from <seller>" (max 1,000 characters, so it cannot pass as UseHourly), and a one-click stop link. `server/invoice-mail.ts` `deliverInvoiceEmail` is the only sender (the button and the reminders both use it).
- **Guards, in one place:** the account must have a CONFIRMED, non-bounced address, not be a sample account, and be at least 24 hours old (`senderBlocker`); the client needs an address that is not on the stop list; 20 sends a day per account and 3 a day per recipient address ACROSS all senders (`hitRateLimit`, atomic; the recipient key is a hash); the per-invoice link cap applies. A failed send turns the link it made back off and records nothing; the user sees a plain message, never the provider's error. Every send is recorded in `invoice_emails` (the history shown in the panel).
- **Stop list:** `email_suppressions`. `/stop-emails` (page with a button) and `POST /api/stop-emails` (the one-click header; GET does nothing) add an address, authenticated by a signed token (`stopEmailToken`, HMAC of the address with AUTH_SECRET). The Resend bounce webhook adds any address that bounced for good or complained, clients included. Once listed, nobody can email that address through UseHourly.
- **Overdue reminders (opt-in, default off):** the checkbox in the panel sets `invoices.remind_overdue`. `server/invoice-reminders.ts` runs from the hourly cron (`/api/cron/weekly-reminders`): the first reminder a day after the due date, the second a week after, never for a paid invoice or one without a due date (`dueReminder`). Each is claimed with one conditional UPDATE on `reminders_sent` (overlapping runs cannot double-send); trouble that may pass (a daily limit, the email service) gives the claim back for the next hour, trouble that will not (no client address, opted out, owner unconfirmed) uses the reminder up. Each reminder carries its own 30-day link.
- Account deletion removes the history; the stop list is about recipients and is kept.
- Test: `invoice-mail-journey.test.ts` (mutation-checked: confirmed-owner rule, stop list, per-recipient cap, link turned off after a failed send, the conditional reminder claim). Not tested against a real mailbox yet: the first live send is the real check (try one to your own address).

## Forms must post (2026-10-17, found in the first-day walkthrough)
- Every `<form>` declares `method="post"`. A form with no method submits with GET when its script has not loaded (a slow phone, a blocked script), which put a typed PASSWORD in the address bar during the walkthrough. `forms-never-use-get.test.ts` fails on any form without it. `next.config.mjs` allows `127.0.0.1` in development (`allowedDevOrigins`), so a second browser session with separate cookies can be used for walkthroughs: register a throwaway user there, then delete it.
- Walkthrough tip: the local robot check needs a real Cloudflare widget, which cannot be clicked in automation, so start the dev server with `TURNSTILE_SITE_KEY= TURNSTILE_SECRET_KEY= npm run dev` for a test run, then restart it normally.

## Performance (2026-10-20)
- **What costs time on D1 is the number of queries IN SEQUENCE (one network round trip each), not rows.** Measure before changing anything: start the dev server with `PRISMA_QUERY_LOG=1 npm run dev` (one `QRY <ms> <sql>` line per query in the server output; `lib/prisma.ts`; never set in production) and load a page with a heavy demo account (seed a few thousand entries with `wrangler d1 execute --local`).
- **One request per page:** the busy pages (Today, Week, Month, Clients, Invoices) start every query they need in the same render, so they go out as ONE batched request. A component that mounts later and asks for something new costs a second round trip, so such queries (budgets, logos, the running timer) are started by the page view itself (same query key, so nothing is fetched twice); the Week page hands the picked day its entries and marked days from the week's own data (`weekSeed`) instead of asking again. `e2e/request-batches.spec.ts` fails if a page needs more than one request.
- **`entry.list`** reads the entries, the non-billable days and the account's projects (with clients) in parallel and joins them in code (Prisma's own include would run entries, then projects, then clients, in a chain; its one-query `relationLoadStrategy: "join"` is not available on SQLite/D1); authors are looked up only when an entry has one. Pinned by `query-budget-journey.test.ts`.
- **Sums come from covering indexes** (migration 0029): `(user_id, project_id, date, minutes)` for all-time per-project sums and `(user_id, date, project_id, minutes)` (it replaced `(user_id, date)`) for date ranges, so `project.totals` never reads entry rows. `project.budgets` no longer loads the account's whole history: a month budget reads that month, a whole-project budget is one SUM plus the few entries on non-billable days (in groups, because D1 allows 100 bound values per query). Check a plan with `wrangler d1 execute DB --local --command "EXPLAIN QUERY PLAN ..."` (look for COVERING INDEX).
- The query client keeps data fresh for a minute (`trpc-provider.tsx`); a mutation still refreshes what it changed at once.

## Local-first spike: entries on the device (2026-10-20, issue #95, migration 0032)
- **What it is:** an opt-in switch (Account > Your data > "Keep a copy on this device (experimental)", localStorage `hourly:localFirst`, per browser, never for sample accounts). With it on, time ENTRIES live in IndexedDB (`hourly-local`, `lib/local-sync/idb-store.client.ts`) and `entry.list` / `entry.nonBillableDays` are answered from there with no network; `entry.create` / `update` / `delete` are applied on the device first and sent in the background, also with no connection. Everything else (timers, clients, projects, invoices, merge, bulk entry) still goes to the server as before; after one of those succeeds the copy is pulled up to date BEFORE the caller hears the answer (`REFRESH_AFTER` in `link.ts`). Off by default, so nothing changes for anyone who does not turn it on. Step 1 of the issue's plan; the hand-built-vs-engine decision is still open.
- **Server:** `entry_changes` (migration 0032) is a change log filled by SQL TRIGGERS on `time_entries` (insert, update, delete), so every write path is covered (app, MCP tools, imports, merge, a project's delete cascading to its entries). It records WHICH entry changed, not how: `sync.pull` (`routers/sync.ts`, `server/entry-sync.ts`) looks each one up (still there = send it whole, gone = list it in `deletes`), so a delete then re-create of one id arrives as one upsert. `cursor: null` = a full copy a page at a time (1,000 by id), with `head` read BEFORE the first page so a change made meanwhile is replayed by the next pull; otherwise changes after `cursor`, 500 log rows per call (`more`). Projects (with clients), non-billable days and author names travel with every pull (small). No foreign key on the table on purpose (the cascade from deleting an account would insert rows pointing at it); `account-deletion.ts` clears it right after the entries, housekeeping sweeps rows older than 30 days (`SYNC_LOG_KEEP_DAYS`), and a device that has not pulled for 14 days starts again from a full copy (`needsFullResync`).
- **Device engine** (`lib/local-sync/`): `engine.ts` `SyncEngine` keeps the server's last copy plus an ordered list of waiting changes (`ops.ts`); what screens see is `withOps` (copy + waiting changes), so an offline change stays visible and an incoming change never disturbs it. Rules, each pinned by a test: the server validates and stays the authority (the device applies the same rules first and refuses with the server's own messages); waiting changes fold together (an edit of a not-yet-created entry joins its creation, two edits become one, a delete of a not-yet-created entry cancels both) but never the one being sent right now; edits carry only the fields touched, so different fields edited on two devices both survive and the same field, the later push wins; a delete beats an edit made elsewhere; a change the server refuses (quota, deleted project) disappears again and `onRefused` toasts the reason; `entry.create` is idempotent by the entry's own id, so two tabs or a lost reply save it once. A copy belonging to another account is wiped, never shown. `link.ts` is the tRPC link in front of the HTTP link (`trpc-provider.tsx`); `components/local-first.tsx` (mounted in the dashboard layout) opens the engine, syncs on start, every 30 s, when the connection returns and when the tab is shown, and tells other tabs through a `BroadcastChannel`. It sets `data-local-first="ready|copying"` on `<html>` (tests wait for it) and gives `entry.list`/`nonBillableDays` queries `networkMode: "always"` while active (react-query would otherwise hold them while the browser is offline, so an offline change would never show). `quick-add.tsx` skips its old offline queue when the engine is ready.
- **Sign-out** (`signOutOfDevice` > `clearLocalCopy`): sends what is waiting (3 seconds at most), then forgets the copy; changes that could not be sent stay for that account (as the old queue does) unless the account is being deleted.
- **Known gaps (spike):** the old "Offline status" banner still says edits and deletes need a connection; timers need a connection; totals, budgets and reports are still computed on the server (they catch up after the push, not instantly); project/client changes made offline are not possible; team members' entries only arrive through the pull; no encryption at rest; the engine reloads its memory from the device database only when another tab says it changed (a `BroadcastChannel` message); nothing measures the real speed benefit yet (the issue's step 1 asks for it).
- **Tests:** `entry-sync-journey.test.ts` (REAL SQLite with every migration applied: triggers, paging, isolation, the pull procedure; mutation-checked), `local-first-journey.test.ts` (two devices: offline add/edit/delete, conflicts, paging, refusals, reopen; mutation-checked: lock on the sending change, account wipe, head position, create dedupe), `local-first-link.test.ts`, `local-first-switch.test.ts`, and `e2e/local-first.spec.ts` (a real browser: switch on, go offline, add, edit and delete, come back, the server has exactly the right entries). `__tests__/helpers/sqlite-sync-db.ts` and `fake-sync-server.ts` are the stand-ins. Deploy order: `npm run d1:migrate:remote` (0032) BEFORE `npm run deploy` (CircleCI does it); locally `npm run d1:migrate:local` and restart the dev server (the Prisma client changed).

## Working offline (2026-10-19, issue #69, no migration)
- **Entries typed offline are kept and sent later, exactly once.** The add form (`quick-add.tsx`) makes a UUID per entry (`clientId`), sends it with `entry.create`, and if there is no connection (`navigator.onLine` false, a network failure, a gateway 502/503/504 or the 20-second timeout set in `trpc-provider.tsx` for `entry.create`) it keeps the entry in localStorage (`hourly:pendingEntries`, `lib/offline-queue.ts`: per account, max 200, validated on read) and shows "You're offline" / "N saved entries to sync" (`components/offline-sync.tsx`, mounted in the dashboard layout; it sends oldest first when the connection returns, the tab is shown or every 30 seconds, and a "Try again" button). **`entry.create` is idempotent:** a `clientId` already saved for the account returns the saved entry, and a lost race returns the winner, so a retry can never make a copy; another account's id is never handed over. An entry the server refuses (for example its project was deleted) stays marked in the list until discarded. Only adding an entry is queued: timers, edits and deletes need a connection (Start timer is disabled offline; mutations use `networkMode: "always"` so they fail at once, and `toastError` says "No connection. That needs you to be online.").
- **The app opens offline.** `public/sw.js` (hand-written, registered by `components/service-worker.tsx` in production, or in a test with `NEXT_PUBLIC_ENABLE_SW=1`) keeps built files cache-first, keeps each `/dashboard/*` page it fetches network-first (not redirects or errors; a copy opens when there is no connection or after 6 seconds of a slow one; a never-opened page falls back to the same page without its query, then to `/offline.html`, never to another page under this address) and touches nothing else (API, sign-in, other pages, non-GET). Both files are public in `route-access.ts`. The page HTML is only a shell, so `components/offline-guard.tsx` also keeps a copy of the everyday queries (`lib/offline-cache.ts`: entry.list, entry.nonBillableDays, clients.list, project.totals, project.budgets; newest 15, under 1 MB, not older than 14 days) in localStorage (`hourly:queryCache`) and puts it back on load. It also provides the signed-in id from the server-rendered layout (`useCurrentUserId`) so nothing needs a network call to know whose entries to send.
- **Privacy on shared devices:** the kept pages and the data copy are cleared on sign-out (`lib/sign-out.ts` `signOutOfDevice`, used everywhere instead of `signOut`; deleting the account also drops the waiting entries) and whenever the signed-in account differs from the copy's owner (`hourly:cacheOwner`). Entries still waiting stay on the device for their own account.
- **Testing gotcha:** `next dev` does not hydrate a page whose live-reload websocket is blocked, even online, so offline page loads cannot be tested against the dev server. `offline-app.spec.ts` needs a production build: `NEXT_PUBLIC_APP_URL=http://localhost:3028 npx opennextjs-cloudflare build`, stop the dev server, `npx opennextjs-cloudflare preview --port 3028`, then `E2E_BASE_URL=http://localhost:3028 npx playwright test e2e/offline-app.spec.ts` (an external run does not delete its `e2e-` accounts: run the SQL in `e2e/global-teardown.ts`). `offline.spec.ts` (queue and retry behaviour) runs on the normal dev server. Unit tests: `offline-entries-journey`, `offline-cache-journey`, `service-worker-journey` (runs the real `sw.js` in a sandbox).

## Not breaking what works: regression policy (2026-10-20)
Why this exists: the day-card "Edit day" button shipped doing nothing, because a rewrite left it unwired and no test ever clicked it. The layers below are what stops that class of bug; keep all of them.
- **Every bug fix ships with a test that fails without it** (prove it: put the bug back, watch the test fail, remove it). Every new control ships with a test that clicks it and checks the RESULT (a form opened, a value saved), not only that it exists.
- **`npm run ci`** (types, lint, the rules scripts, 590+ unit tests, coverage floor) runs on every push and pull request. **`npm run e2e`** (the real-browser suite, desktop and phone, about 50 tests) now runs on **every pull request** too (`.github/workflows/e2e.yml`), as well as nightly: a pull request that breaks something a person can click shows a red check before it is merged and deployed.
- **`npm run e2e:sweep`** (`e2e/every-control.spec.ts`, nightly and before a release; slow) opens each page with sample data and CLICKS EVERY button, tab and radio, failing on any that does nothing: no change elsewhere on the page (a control that only flips its own label does not count), no new address, request, download or tab. It also requests every link on those pages. A control that legitimately shows nothing goes in its `QUIET` list with a reason; an already-selected tab or radio is skipped. It was checked by putting the "Edit day" bug back: it fails with it, passes without.
- **Toggles:** a button that opens a form must close it on the second click and report `aria-expanded` (`IconAction expanded`, the Edit buttons); `e2e/toggles.spec.ts` covers them. A card shown in "edit mode" through a prop that is only read when it first appears must be re-keyed when the prop changes.
- **The e2e copy of the app uses its own database folder** (`.wrangler/state-e2e`, `E2E_PERSIST`): never run two servers on the same local D1 files (it produced "Failed to get session commit token" and flaky failures). After a production-build test, kill the preview AND its `wrangler`/`workerd` children (they keep holding port 3028 and the local database).
- Still manual (needs a human or a real account): Google and GitHub sign-in, real email delivery, Xero and QuickBooks imports, the look of a printed or PDF invoice.

## Security notes
- Security headers (nosniff, frame deny, HSTS, referrer, permissions) are set in `next.config.mjs`. **The Content-Security-Policy is nonce-based (2026-10-18):** `src/proxy.ts` makes a fresh nonce per request and sets the policy built by `src/lib/csp.ts` on the request (so Next.js puts the nonce on its own inline scripts) and the response; the root layout reads `x-nonce` for the theme boot script. There is NO `'unsafe-inline'` for scripts (styles still allow it). Every page now renders per request (reading the nonce makes them dynamic). Any new inline `<script>` needs `nonce={nonce}` (a JSON-LD `application/ld+json` block does not run, so it needs none); a script loaded from another host must be added to `script-src` in `csp.ts`. Test: `csp.test.ts`; the browser tests fail on any CSP violation (they fail on console errors). Verified against a production build (`npm run preview`): every script tag carried a nonce.
- CSV exports prefix text that starts with = + - @ with an apostrophe (`csvField` in `src/lib/export-all.ts`) so a note cannot run as a spreadsheet formula.
- `removeConsole` keeps `console.error` in production: the tRPC route logs internal errors with it.
- `.github/workflows/ci.yml` (GitHub Actions) and `.circleci/config.yml` (CircleCI) both run biome, tsc and vitest on every push. CircleCI also deploys `main`: it writes `wrangler.jsonc` from env vars (`scripts/ci-wrangler-config.mjs`), applies D1 migrations, then `npm run deploy`. Env vars are listed in the README. Both run the single `npm run ci` command (package.json), so they cannot drift; GitHub Actions is the one forks and pull requests see (CircleCI has the deploy secrets).
- Sign-in and sign-up are throttled (`src/lib/rate-limit.ts`, D1 `rate_limits`). Sessions carry `token_version`; a password change or "Log out on all devices" bumps it and `createContext` plus the dashboard layout reject older tokens (`src/lib/session-version.ts`).

- **Abuse limits (2026-10-17 audit).** `hitRateLimit` is atomic: a conditional UPDATE opens a fresh window and `count = count + 1` counts each hit, so a burst of parallel requests cannot be undercounted (never go back to read-then-write; `rate-limit.test.ts` fires 80 at once). `src/lib/request-limits.ts` throttles changes (POST) on `/api/trpc` in `createContext`: 240 CALLS a minute per account, 60 per connection before sign-in (a batch of 20 costs 20: it used to count once, which let batching multiply the limit); reads are not counted. `maxBatchSize` (`MAX_BATCH` in `lib/trpc-limits.ts`, 20, also the browser link's `maxItems`) caps calls per HTTP request; the handler lives in `server/trpc-handler.ts` so tests can drive it. `src/lib/quotas.ts` caps what one account may store (200 clients, 500 projects, 50,000 entries, 2,000 invoices) and is checked in the create paths. Login compares against a dummy bcrypt hash for unknown addresses (`lib/password.ts`) so timing does not reveal accounts. Tests: `security-hardening.test.ts`, `rate-limit.test.ts`; `__tests__/helpers/memory-rate-limit.ts` is the shared fake limiter table. Changing the limits means changing the constants, not the call sites.

- Email (`src/lib/mailer.ts`, Resend over `fetch`): confirmation link on register and from the Account page, and password reset (`/auth/v2/forgot-password`, `/reset-password`, `/verify-email`). One-time tokens live hashed in `email_tokens`; a reset bumps `token_version`. Everything is dormant until `RESEND_API_KEY` and `EMAIL_FROM` are set as Worker secrets (`ctx.mailer` is null; pages say email isn't set up). Tests: `src/__tests__/email-flows.test.ts`.
- The CSP (see above; set per request in `src/proxy.ts`) blocks injected scripts, framing, plugins, `<base>`, off-site fetches and forms. Checked in a browser on every page, an Excel export, the zip export and an invoice PDF with no violations.

## MCP server (AI assistants), added 2026-10-17
- Endpoint `POST /api/mcp` (Streamable HTTP, stateless, JSON replies; GET/DELETE answer 405). Same Worker and D1 as the app, no extra backend. `/api` is outside the sign-in proxy, so the route does its own auth.
- **Auth = personal access tokens** (`uh_` + 43 chars). Made, listed and revoked on Account > "AI assistants" (`src/components/api-tokens-card.tsx`, `account.createApiToken / listApiTokens / revokeApiToken`; these need a browser session, no MCP tool exposes them). Table `api_tokens` (migration 0010) keeps only the SHA-256, a display prefix, `access` ("read" | "write"), `expires_at`, `last_used_at`, `revoked_at`, and the account's `token_version` at creation: a password change or "Log out on all devices" kills every token (same rule as sessions, `sessionStillValid`). Max 20 live tokens per user.

Tool failures return `isError` with a plain message; raw database errors never leave the server.

## MCP OAuth (2026-10-17)
- MCP clients can connect with "log in and approve" instead of a pasted token. OAuth 2.1: dynamic client registration (`POST /api/oauth/register`, public clients only, no secret), authorization code + PKCE S256 only, no refresh tokens (the access token lives 90 days, then the client asks again).
- Discovery: `/.well-known/oauth-protected-resource` (also `/api/mcp` suffixed) and `/.well-known/oauth-authorization-server`; the MCP 401 carries `WWW-Authenticate: Bearer ... resource_metadata=...`.
- Consent screen `/oauth/authorize` (public route; it sends signed-out users to `/auth/v2/login?next=...`, which both login paths honour through `safeNext`). It must read parameters with `useSearchParams`, NOT `window.location` (right after login the URL is stale during the client navigation). Shows the client's self-declared name as plain text and the exact redirect host; user picks read-only or read-and-change; demo accounts are refused.
- Rules: redirect URIs exact-match what the client registered; a bad client/redirect is never redirected to; codes are 5 minutes, hashed, single use, claimed atomically before anything else is checked (a wrong verifier burns the code); reuse revokes the token the code made; approvals 20/hour per user, registrations 20/hour per IP, token calls 60/min per IP. The result is an ordinary `api_tokens` row named "<client> (OAuth)", so it shows in Account and dies on password change. Connecting the same app again replaces its earlier token.
- Code: `src/lib/oauth.ts` (pure rules), `src/server/oauth.ts`, `src/server/routers/oauth.ts`, routes under `src/app/api/oauth/` and `src/app/.well-known/`, page `src/app/oauth/authorize/`. Tables `oauth_clients`, `oauth_codes` (migration 0013). Test: `oauth-journey.test.ts` (mutation-checked: PKCE, redirect matching, atomic claim); also verified in a real browser end to end.
- Deploy order: `npm run d1:migrate:remote` (0013) BEFORE `npm run deploy`.

## Security hardening (2026-10-17, issue #29)
From a deep review of the public site (no cross-tenant access, no auth bypass, no secrets in history were found; the findings were abuse, availability and a few edge cases). Rules to keep:
- **Client addresses:** never read `cf-connecting-ip` directly. `clientIpFrom(headers)` (`src/lib/client-ip.ts`) buckets IPv6 by /64 (a customer owns 2^64 addresses; a raw-address key limits nothing) and unwraps IPv4-mapped addresses. A test greps `src/` and fails on a raw read.
- **Limits count calls:** tRPC writes by procedure call (`callsInTrpcRequest`), MCP by message (batches capped at 20, each message costs 1). `hitRateLimit(..., cost)` takes a cost.
- **Invoice storage:** logos are NOT copied into invoice snapshots any more. They live once per distinct image in `invoice_logos` (hash-keyed, per user, max 30), the snapshot holds `logoHash`, `invoice.get` puts the logos back (`server/invoice-logos.ts`), `invoice.create` returns them inline for the PDF, deleting an invoice releases logos nothing else uses. A snapshot over 900,000 characters is refused, search text is cut at 50,000, an invoice period is at most 366 days. Older invoices keep their inline logos. Logo size limits: 300,000 characters (business/client), 100,000 (project).
- **Reads:** `entry.list` takes at most 366 days; `entry.listAll` pages 2,000 at a time (used by "export everything"). Dates must be real calendar dates (`isRealDate`).
- **Social sign-in takeover:** linking Google/GitHub to an account that has a password ALWAYS takes it over (password cleared, `token_version` bumped), even if its email was confirmed, because anyone can register with someone else's address and pick the password. A provider-made account without a password is just linked.
- **Sign-in and reset throttles** (`lib/login-throttle.ts`, `lib/rate-limit.ts`): per connection, per address+connection (10/15 min), and a high per-address ceiling (100/15 min), so a stranger cannot lock the owner out. Reset: per connection, per address+connection (3/h), per address (20/h). `changePassword` allows 5 wrong guesses per 15 minutes. Email addresses are capped at 254 characters (`emailField`).
- **OAuth consent:** apps are labelled unverified, the full redirect address is shown, "Read only" is always preselected (whatever scope the app asked for), nothing redirects automatically on a malformed request, redirect schemes that launch programs are refused (`BLOCKED_SCHEMES`, `ms-*`), and client names are cleaned of control/bidi characters (`cleanClientName`).
- **Housekeeping:** the hourly cron route also sweeps spent `rate_limits`, expired email links and expired OAuth codes (`server/housekeeping.ts`), even when email is not set up.
- **Small things:** `/api/session-expired` only signs out a session that is really stale; the dashboard layout redirects signed-out visitors itself; MCP token access fails closed to read-only; `X-Powered-By` is off; `/.well-known/security.txt` is published (renew its Expires date by 2027-10-17); CI uses `permissions: contents: read` and SHA-pinned actions.
- **Not done (tracked in #29):** CircleCI deploy token (a context restricted to main now exists; finish by moving the token into it, see the Launch gaps section), self-service account deletion and a fuller privacy page, OAuth token replacement matches on display name, bot protection on sign-up.
- Deploy order for this change: `npm run d1:migrate:remote` (0015) BEFORE `npm run deploy`.

## stdio bridge (2026-10-17, issue #27)
- `bridge/` is a zero-dependency Node script (`usehourly-mcp`, `node bridge/index.mjs`) that speaks MCP over stdio and forwards `tools/call`, `resources/read` and `prompts/get` to the hosted endpoint with `USEHOURLY_API_TOKEN` as the bearer. The handshake and the tool/resource/prompt lists are answered locally from `bridge/catalog.json` (generated by `mcpCatalog()` in `protocol.ts`: `npm run mcp:catalog`), because the live endpoint returns 401 without a real token and Glama's build only has a dummy one.
- It exists because Glama only scores a server (Server Coherence, Tool Definition Quality) after a Docker "release", and that build starts the repo as a stdio server through `mcp-proxy`; the auto-inferred build ran `next start` and timed out. Glama's Dockerfile page is configured to build the repo and run `mcp-proxy -- node bridge/index.mjs`.
- Adding or changing a tool means running `npm run mcp:catalog` and committing `bridge/catalog.json`; `mcp-bridge.test.ts` fails on drift. The bridge treats a reply as JSON-RPC only when it has `jsonrpc: "2.0"`, because the server's 401/403/413/429 bodies are plain `{ error }` (found by the test). **Published on npm as `usehourly-mcp`** (account `denis.zontak`, 2FA on; issue #28; 1.0.0 went out 2026-10-17, 1.0.1 added `mcpName`). The official MCP registry only accepts an npm package whose `package.json` has `mcpName` equal to the server name in `server.json` (`app.usehourly/usehourly`), and the entry must name that exact package and version: `mcp-bridge.test.ts` checks this. **To release a change (automatic since 2026-10-20):** bump `version` in `bridge/package.json` AND `server.json` (top-level and `packages[0]`), run `npm run mcp:catalog` if tools changed, and merge to `main`: `.github/workflows/publish-bridge.yml` publishes to npm (trusted publishing, no stored token, provenance) and then to the MCP registry (needs the repository secret `MCP_REGISTRY_KEY` = the contents of `~/.config/mcp-registry/usehourly.hex`; skipped with a log line without it; the registry's `description` limit is 100 characters). By hand, if ever needed: `cd bridge && npm publish --access public` (the owner's passkey/2FA, in a normal terminal), then `mcp-publisher login http --domain usehourly.app --private-key "$(cat ~/.config/mcp-registry/usehourly.hex)"` and `mcp-publisher publish`. The tool list is baked into each version, so `npx` users see a new tool only after a new version is published. The bridge refuses non-https endpoints (loopback http is fine) and never follows redirects.
